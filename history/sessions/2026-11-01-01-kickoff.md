# Session 2026-11-01 #01: Kickoff, Phase 1 (a working CLI), then the web app

- **Who:** Andrei (owner) + Claude (AI pair)
- **Goal:** refine ("lapidate") the idea, create the repo with a memory folder, and find out whether the
  official map can be read programmatically. The session went on to build the whole Phase 1 CLI.

## The original idea (as stated by Andrei)

A route manager for Inhotim that generates the **shortest route to visit everything in the least
amount of time**. Inhotim often adds and removes exhibitions, so the app should read the official map
(<https://www.inhotim.org.br/mapa/>) dynamically, build a graph from it and calculate the route.
GPS tracking of visitors could come later; it isn't the focus now.

## What happened

1. **Research spike on the official map.** The headline finding: the data is reachable *without*
   scraping HTML:
   - `GET /wp-admin/admin-ajax.php?action=get_markers` (the same call the website's Google Map makes)
     returns every marker **with lat/lng**, category, route color ("eixo") and artists.
     262 entries / 150 unique ids on 2026-11-01.
   - The colored walking routes ("eixos": laranja, amarelo, rosa) are an SVG overlay. The theme JS
     hardcodes the overlay's geographic bounds, so the SVG paths can be **georeferenced**. Overlaid on
     OpenStreetMap they line up within a few meters.
   - OpenStreetMap has the park boundary (relation 5418784) and a decent footpath network
     (~11 km footways, ~12 km service roads, ~7 km tracks/paths in the area).
   - Full write-up: [`docs/data-sources.md`](../../docs/data-sources.md).
2. **Refined the problem** (see [`docs/vision.md`](../../docs/vision.md)):
   "visit everything in the least time" is a TSP. A rough estimate (~60 stops plus dwell times plus
   walking) suggests it won't fit in one day, so the more useful question for a real visitor is
   *"what's the best route for the time I have?"* That's the **Orienteering Problem**, and multi-day
   is the Team Orienteering Problem. The same solver (OR-Tools) handles all three.
3. **Repo created:** <https://github.com/Andreixzc/inhotim-path> (public), with this `history/` folder and
   `CLAUDE.md` so future sessions start with context.
4. **Phase 1 built** (commits `5310f7c` → `9df15e6`, all on `main`):
   - `fetch`:
     - marker feed → `data/pois.json`: 150 POIs, names NFC-normalized, deterministic dedupe;
     - routes SVG → `data/axes.geojson`;
     - OSM via Overpass → `data/osm.json`, rotating mirrors with backoff, since the main server returned 502s.
   - Walking graph: 16.3 km of OSM paths plus 2.5 km of official-route gap fills and 79 connectors, for
     20.4 km, 492 nodes and 565 edges. Every POI is reachable; the median snap is ~10 m, the max 63 m
     (Yayoi Kusama).
   - Walking matrix (one Dijkstra per stop), a CP-SAT solver, the planner, outputs (itinerary, GeoJSON,
     Leaflet HTML), the `route` command, README figures (`scripts/plot_route.py`) and GitHub Actions CI.
   - 116 tests. Planner and CLI run end to end on a synthetic park with hand-checkable distances.
5. **Results** (4 km/h; 20 min per gallery, 8 per outdoor work, 10 per garden):
   - **Everything: 58 stops, 11.8 km walking (2h57) + 11h50 at stops = 14h47**, proven optimal in ~0.2 s.
     This confirms the "more than one day" framing.
   - 6 h: 24 stops (10 galleries, 11 outdoor works, 3 gardens) with 40 min of walking.
   - 4 h: 17 stops (6 / 9 / 2) with 27 min of walking.
6. **Solver detour.** With the OR-Tools routing library, `--budget 6h --must kusama "beam drop"` found *no
   route at all*. Greedy arc extension spends the budget, then backtracks until the time limit. Benchmarks
   showed that no first-solution strategy was best everywhere. A CP-SAT circuit model beat every strategy in
   every scenario and proves optimality or bounds. Switched → [ADR 0004](../decisions/0004-cp-sat-circuit-solver.md).
7. **Value-model detour.** Per-kind weights (gallery 10, outdoor work 6, …) made a 4 h route with *zero*
   galleries, and raising the gallery weight flipped it to galleries only. A stop is now worth its viewing
   minutes → [ADR 0005](../decisions/0005-stop-value-is-viewing-time.md).
8. **Blocked map tiles.** Andrei opened the HTML map and every tile was OSM's block tile ("App is not
   following the tile usage policy…"). A page opened from a file sends no `Referer`, which OSM's tile policy
   requires. CARTO now needs an API key, so the page moved to MapLibre GL on OpenFreeMap's vector tiles (no key,
   CORS) → [ADR 0006](../decisions/0006-basemap-openfreemap.md). Checked in Chrome from a local file: desktop
   and phone-sized views, popups, and the plain-background fallback when the basemap is unreachable.
9. **Direction set:** Andrei wants *"a simple webapp to help people plan their routes before or when they are
   already there"* ([vision](../../docs/vision.md)). Andrei also asked how times are estimated:
   - walking = shortest path ÷ 4 km/h;
   - plus a fixed time per kind of stop;
   - no slope, queues or breaks yet.
10. **Satellite view.** Esri's keyless imagery, the one most examples use, isn't licensed outside Esri software.
    MapTiler's free plan has no card and pauses at its quota instead of billing. Added `--satellite-key` (or
    `$MAPTILER_API_KEY`) → [ADR 0008](../decisions/0008-satellite-view-maptiler.md). Checked in Chrome:
    - no key: no button and no MapTiler requests;
    - bad key: the button disables itself, and nothing is requested before the first press.
    Real imagery is not checked yet: there's no key.
11. **Data that refreshes itself.** `fetch` now reports what's new (POIs added, removed, renamed or moved). A
    daily GitHub Action (06:17 BRT) fetches, tests, and commits only real changes →
    [ADR 0007](../decisions/0007-daily-data-refresh.md).
    - The first manual run on GitHub (2026-11-01, 14:57 UTC) reached every source, found nothing new and
      made no commit.
    - The commit-and-push path was tested in a local git sandbox, including `main` moving mid-job.
12. **The web app** (Andrei: *"start the web app"*), as a static site that plans in the browser →
    [ADR 0009](../decisions/0009-web-app-plans-in-the-browser.md). Commits `86ebf47` → `6f2ca28`:
    - `inhotim-path web-data` exports the park: 149 of 150 POIs on the network, 548 nodes, 621 edges, 74 KB.
    - `web/js/`: Dijkstra and GPS snapping; a solver that is exact up to 12 stops (Held-Karp) with iterated
      local search beyond; a planner mirroring `planner.py`; then the page (form, itinerary, map, worker,
      Portuguese and English, shareable links, start from "my location").
    - Tests: brute force on small instances, for both the exact and the heuristic paths. A pytest test plans the
      synthetic park with both planners and checks that they agree. CI runs the node tests too.
    - Tuning: one long search often ended a couple of minutes of art short of CP-SAT. Four shorter independent
      searches, carrying on from routes worth as much, did better: against CP-SAT given 30 s, the same value in
      100 of 115 runs, never more than 2 minutes short, median 107 ms on a laptop (`scripts/benchmark_web_solver.py`).
    - Checked in Chrome with Playwright, at desktop and phone sizes, in light and dark mode. Changing the budget,
      search and must-sees, skip, popups, Portuguese, a mocked GPS fix inside the park (the route starts there
      and ends at the reception), one 451 km away (it falls back to the reception and says why), and shared
      links all worked.
    - Two fixes from those checks:
      - MapLibre's expanded attribution, long with our credits, hid part of the route. The map now shows short
        credits; the full ones are in the panel.
      - Collapsing the panel turned the summary back into "Loading…".
    - `pages.yml` deploys `web/` after CI passes on `main`, and the daily refresh starts it after a data commit. Pages
      is **not switched on yet**: the workflow checks first and only leaves a notice. Switching it on publishes a
      public site, so that's Andrei's call.

## Decisions

- [0001](../decisions/0001-official-map-marker-feed-as-poi-source.md): POIs come from the official `get_markers` feed.
- [0002](../decisions/0002-walking-network-osm-plus-official-axes.md): walking network = OSM + official axes SVG (gap filling).
- [0003](../decisions/0003-python-uv-ortools.md): Python + uv for the pipeline; OR-Tools for routing.
- [0004](../decisions/0004-cp-sat-circuit-solver.md): CP-SAT circuit model instead of the routing library.
- [0005](../decisions/0005-stop-value-is-viewing-time.md): a stop is worth its viewing minutes.
- [0006](../decisions/0006-basemap-openfreemap.md): the HTML map's basemap is OpenFreeMap (MapLibre), not OSM's tile servers.
- [0007](../decisions/0007-daily-data-refresh.md): a daily GitHub Actions refresh keeps `data/` current.
- [0008](../decisions/0008-satellite-view-maptiler.md): satellite view from MapTiler, with the user's own key.
- [0009](../decisions/0009-web-app-plans-in-the-browser.md): the web app is a static site that plans routes in the browser.

## Open questions

- Realistic **dwell times**? They now set both the timeline and the priorities (ADR 0005). Per-gallery
  values could come from the works inside each gallery (`work_in_gallery` POIs).
- Should the **electric carts** (paid shuttles) be modeled as faster edges?
- Per-gallery **opening hours / time windows**? Not in the marker feed.
- Which paths are **steep / not accessible**? Needs elevation data (phase 2).
- CP-SAT runs with 8 threads under a wall-clock limit, so two runs can differ slightly. Is reproducibility
  worth deterministic time limits?
- **Closing time:** starting from "my location" at 13:00 with 6 h ends at 18:57, after the park closes. Opening
  hours aren't in the data; the page only says to check them. Should "time available" offer "until closing"?
